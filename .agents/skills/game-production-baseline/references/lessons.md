# 제작 과정에서 확인된 교훈

## 공통으로 유지할 것

- 새 제품은 하네스의 Git 이력을 이어받지 않고 새 저장소에서 시작한다.
- 기술·게임·아트 제안은 병렬로 조사할 수 있지만, 구현 전에는 하나의 수직 조각과 비범위로 통합한다.
- 도구는 익숙함보다 배포 대상, 편집 방식, 자동 검증 가능성, 팀 역량으로 고른다.
- 핵심 정체성 자산은 직접 제작하거나 절차적으로 만들고, 무료 에셋은 보조 역할과 명확한 라이선스가 있을 때만 넣는다.
- 레벨 수를 늘릴 때는 숫자 상승뿐 아니라 공간과 목표 수행의 학습 단계를 설계한다.
- 자동 상태 검사는 시뮬레이션 오류를, 실제 화면은 판독과 배치 오류를 찾는다. 둘 다 필요하다.
- 공개 문서는 제작 기술보다 방문자가 플레이를 이해하고 실행하는 데 필요한 정보를 우선한다.

## 재작업에서 얻은 것

### 레벨은 수치 테스트만으로 닫히지 않는다

충돌 수치가 유효해도 출구 병목, 적 스폰과 건물 겹침, 사실상 막힌 통로가 남을 수 있다. 자동 입력 완주와 스크린샷을 레벨 데이터 검사 뒤에 실행한다.

### 게임 필은 이벤트 계약으로 만든다

타격 효과를 임의의 애니메이션 목록으로 추가하지 않는다. 사격, 명중, 피해, 처치, 이동기, 목표와 전환 이벤트에 시각·음향·상태 피드백을 연결하고 수명과 우선순위를 검증한다.

### 녹화 성능과 게임 성능은 다른 문제다

고정 tick 여러 개를 한 캡처 프레임에 반영하면 플레이 영상은 끊기고 소리는 몰린다. 녹화 중에는 렌더 한 번당 게임 tick과 실제 시간의 대응을 유지하고, 스크린샷 같은 느린 작업을 전투 루프에서 분리한다.

### A/V 싱크는 사건 단위로 본다

오디오와 비디오 stream 끝점 차이가 작아도 구역 전환 소리가 늦거나 비어 보일 수 있다. 완료 frame, 다음 구역 첫 frame, 타격 frame의 파형을 따로 측정한다.

### 공개 문체도 품질 항목이다

명령형 구호, 추상 서사, 균형 잡힌 홍보형 나열은 실제 게임 정보를 흐릴 수 있다. 게임 방식, 실행, 조작, 현재 범위를 사실 문장으로 쓰고 공개 화면까지 같은 기준으로 검색한다.

## 특정 게임에만 남길 것

장르명, 세계관, 레벨 수, 타이머, 적 수, 색상, 점수, 특정 키 배치, Canvas·Web Audio 선택과 해시는 프로젝트 기록이다. 새 게임의 기준선으로 복사하지 말고 새 제품 가설에 맞게 다시 결정한다.
