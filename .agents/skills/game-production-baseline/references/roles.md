# 역할과 인수인계

역할은 직함이 아니라 책임 경계다. 작은 프로젝트에서는 한 에이전트가 여러 역할을 맡아도 되지만, 같은 결과물을 만든 역할과 승인한 역할은 가능하면 분리한다.

| 역할 | 먼저 받는 정보 | 책임과 산출물 | 통과 증거 | 다음 인계 |
|---|---|---|---|---|
| 코디네이터·프로듀서 | 사용자 목표, 예산, 일정, 저장소 상태 | 헌장, 범위/비범위, 보드, 작업 분해, 게이트 판정 | Doing 제한, 완료 조건, 위험·의존성, 통합 검증 | 모든 역할 |
| 게임 디자이너 | 대상 플레이어, 세션 길이, 장르 제약 | 플레이어 약속, 핵심 루프, 규칙, 보상·실패, 밸런스 가설 | 한 문장 루프와 측정 가능한 성공 기준 | 시스템·레벨·UX |
| 스토리텔러·내러티브 | 게임 규칙, 톤, 콘텐츠 예산 | 세계관 제약, 플레이 중 전달할 정보, 용어표, 짧은 텍스트 | 텍스트가 행동을 설명하고 플레이를 막지 않음 | UX·레벨·공개 문구 |
| 기술 설계자 | 플랫폼, 배포, 팀 역량, 자동화 요구 | 엔진/스택 결정, 모듈 경계, 상태·시간·저장 계약, ADR | 최소 빌드와 위험한 통합의 기술 스파이크 | 프로그래머·QA |
| 게임플레이 프로그래머 | 규칙, 상태 계약, 완료 조건 | 입력 가능한 수직 조각, 테스트 훅, 오류 처리 | 실제 입력으로 시작부터 결과까지 재현 | 레벨·QA·피드백 |
| 레벨·콘텐츠·퍼즐 디자이너 | 핵심 규칙, 도전 단위, 목표 난이도 | 시나리오, 규칙 조합, 공간·자원·정보 배치, 해법·실패 경로, 학습 곡선 | 완료 가능성, 교착·우회 해법, 난도 증가 이유 | 게임플레이·QA |
| 그래픽·UX 디자이너 | 상태 우선순위, 입력, 화면 크기, 접근성 | 기능 팔레트, 실루엣, HUD, 조준·피격·목표 피드백 | 한 프레임 판독, 축소 화면, 색 외 중복 신호 | 구현·QA |
| 사운드 디자이너 | 이벤트 목록, 우선순위, 음량 예산 | SFX 언어, 믹스 우선순위, 음소거/접근성, 출처 | 이벤트별 식별, 과밀 구간에서도 핵심 신호 청취 | 구현·QA·영상 |
| 에셋·라이선스 담당 | 필요한 자산 목록, 스타일, 저장소 정책 | 제작/다운로드 결정, 출처·라이선스·해시·변환 기록 | 모든 반입 파일의 재배포 조건 확인 | 아트·사운드·릴리스 |
| QA·플레이테스트 | 빌드, 규칙, 위험, 완료 조건 | 자동 회귀, 실제 입력 경로, 기기/해상도, 관찰 스크립트 | 상태·화면·소리·런타임 로그, 재현 절차 | 코디네이터 |
| 릴리스·쇼케이스 | 검증 빌드, 대상 방문자, 배포 채널 | 클린 빌드, README, 플레이 영상, 크레딧, 릴리스 메모 | 링크·미디어 무결성, A/V 싱크, 새 환경 실행 | 사용자·회고 |

## 인수인계 형식

각 역할은 다음 다섯 항목만 전달한다.

1. 결정한 것과 결정하지 않은 것
2. 수정하거나 만든 파일·산출물
3. 실행한 검증과 결과
4. 남은 위험과 실패 조건
5. 다음 역할이 내려야 할 결정

## 역할 배치 원칙

- 제품 방향, 기술, 아트/에셋 조사는 사전 제작에서 병렬화할 수 있다. 코디네이터가 충돌을 해결한 뒤 한 계획으로 잠근다.
- 동일 구현 파일을 여러 역할이 동시에 수정하지 않는다.
- 구현자와 독립 검토자는 같은 완료 주장을 공유하지 않는다.
- 코드 모델이나 도구를 지정했다면 접근 가능성을 먼저 확인하고, 불가할 때의 대체 경로를 기록한다.
- 사람의 재미 판단은 인간 플레이테스터 역할로만 닫는다.
